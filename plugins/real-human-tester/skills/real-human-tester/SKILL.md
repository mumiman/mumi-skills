# Real Human Tester — คนใช้จริง

เข้าไปใช้ Web/Mobile app จริงในฐานะ "คน" ทีละบทบาท แล้วรายงานว่าคนจะติดตรงไหน มีสอง mode คือให้ feedback อย่างเดียว และให้ feedback แล้วแก้แอปต่อเลย

## แนวคิดที่อยู่เบื้องหลัง

คนสร้างแอปรู้จักแอปดีเกินไป จึงมองไม่เห็นว่าคนใช้จริง "โง่กว่าที่คิด" คนจริงอ่านข้าม คลิกผิด พิมพ์ผิด บางครั้งไม่รู้ด้วยซ้ำว่าแอปนี้มีไว้ทำอะไร หรือไม่รู้ว่ามี feature นี้อยู่ แอปที่ดีคือแอปที่คนแบบนี้ยังไปถึงเป้าหมายได้ด้วยเส้นทางที่ง่ายที่สุด

หลักที่ใช้ตัดสินใจตลอดทั้ง skill:

- **คนไม่ perfect และต้องบังคับด้วยกฎ** Claude อ่านทุกตัวอักษรบนหน้าได้ในทันที ซึ่งคนทำไม่ได้ ถ้าแค่ "แสดง" ว่างง ผลที่ได้คือการเดาของ Claude จึงต้องใช้กฎที่จำกัดการมองและการกระทำจริง ๆ
- **ผู้ทดสอบเห็นแค่หน้าจอ** การรู้ code ทำให้รู้ว่าปุ่มอยู่ไหนโดยไม่ต้องหา มุมมองผู้ใช้จึงเพี้ยน
- **แยกสิ่งที่เห็นว่าพัง ออกจากสิ่งที่เดาว่าคนจะลำบาก** สองอย่างนี้น่าเชื่อไม่เท่ากัน และผู้ทดสอบจำลองไม่ใช่เจ้าหน้าที่ที่เหนื่อยและถูกเร่งงานจริง
- **ความง่ายชนะ style เมื่อสองอย่างชนกัน** คนที่ไปไม่ถึงเป้าหมายไม่มีโอกาสเห็นความสวยของแอป
- **แต่งานต้องมี class** หลังทำให้ง่ายแล้ว ให้แต่งสิ่งที่ง่ายนั้นให้มีลายเซ็นที่จำได้ ด้วยสิ่งที่ไม่กินความเข้าใจ เช่น ตัวอักษร สี น้ำเสียง และความประณีตสม่ำเสมอ
- **ลดก่อนเพิ่ม** ความงงส่วนใหญ่แก้ได้ด้วยการตัด รวม หรือเปลี่ยนชื่อ การเพิ่ม feature เป็นทางสุดท้าย
- **ผู้ใช้เป็นผู้ตัดสิน** ไม่มีการแก้ code ก่อนผู้ใช้เลือก

## เลือก mode

- **Mode feedback** ทำขั้นที่ 1 ถึง 4 แล้วหยุด ไม่แตะ code
- **Mode แก้ไข** ทำครบขั้นที่ 1 ถึง 7

ถ้าผู้ใช้ไม่ได้บอก mode ให้ถามหนึ่งคำถาม Mode แก้ไขต้องเข้าถึง source code ได้ และควรสร้างผู้ทดสอบเป็น agent แยกได้ ถ้าเข้าถึง code ไม่ได้ ให้บอกผู้ใช้ตรง ๆ ว่ารอบนี้ทำได้เฉพาะ mode feedback

## สิ่งที่ต้องมีก่อนเริ่ม

- **ทางเข้าแอป** URL ของแอปที่รันอยู่ และเครื่องมือ browser ที่คลิกและกรอกได้จริง ถ้าไม่มี browser ให้บอกผู้ใช้ว่า skill นี้ทำงานไม่ได้ อย่าทดแทนด้วยการอ่าน code แล้วจินตนาการ
- **Account ทดสอบครบทุกบทบาท** ผู้ทดสอบจะสร้างและส่งข้อมูลจริงในระบบ จึงควรใช้ระบบทดสอบ ถ้ามีแต่ระบบใช้งานจริง ให้ถามผู้ใช้ก่อนทุกการกระทำที่ส่ง อนุมัติ หรือลบ
- **ข้อมูลที่กรอกต้องเป็นข้อมูลสมมติ** ที่เห็นชัดว่าปลอม ห้ามใช้ข้อมูลบุคคลจริง
- **อุปกรณ์** ถามว่าผู้ใช้จริงใช้มือถือหรือคอมพิวเตอร์ ถ้าใช้มือถือ ให้ย่อหน้าจอ browser เป็นขนาดมือถือก่อนทดสอบ

## ขั้นที่ 1 — เตรียมตัว

session หลักสำรวจแอปแล้วร่างของต่อไปนี้ให้ผู้ใช้ยืนยัน ควรใช้เวลาผู้ใช้ไม่เกิน 15 นาที

1. **ตารางบทบาท** มีบทบาทอะไรบ้าง เรียงตามลำดับงานจริง (เช่น คนกรอก คนตรวจ คนอนุมัติ) พร้อมหนึ่งประโยคต่อบทบาทว่าเขาต้องได้อะไรกลับไป
2. **งานหลัก 3-5 งานต่อบทบาท** เขียนเป็นภาษาคน เช่น "สร้างรายงานเหตุการณ์ใหม่หนึ่งฉบับ" ห้ามเอ่ยชื่อปุ่ม เมนู หรือหน้า เพราะจะเป็นการใบ้ทาง
3. **งานส่งไม้ต่อ** งานสุดท้ายของบทบาทหนึ่งต้องสร้างของจริงทิ้งไว้ในระบบ และงานแรกของบทบาทถัดไปคือรับของชิ้นนั้น มีงานตีกลับอย่างน้อยหนึ่งงาน เพื่อดูว่างานย้อนกลับไปถึงคนก่อนหน้าไหม
4. **รายการ feature ต่อบทบาท** ทุกอย่างที่บทบาทนั้นทำได้ในแอป รายการนี้เก็บไว้ที่ session หลัก ไม่ส่งให้ผู้ทดสอบ
5. **ลายเซ็นของแอป** 3-5 บรรทัดว่าอะไรทำให้แอปนี้เป็นงานของผู้ใช้ เช่น น้ำเสียง สีและตัวอักษร ถ้าผู้ใช้ยังไม่มี ให้เสนอร่างจากสิ่งที่เห็นในแอป

รอผู้ใช้ยืนยันก่อนไปขั้นที่ 2

## ขั้นที่ 2 — คนงง ๆ ลองใช้แอป

### ใครเป็นผู้ทดสอบ

สร้างผู้ทดสอบเป็น agent แยกหนึ่งตัวต่อบทบาท ส่งให้เฉพาะ URL ข้อมูล login คำบรรยายตัวตนหนึ่งย่อหน้า (เป็นใคร ทำงานในสถานการณ์แบบไหน ใช้อุปกรณ์อะไร) กฎด้านล่าง และงานที่ต้องทำ ไม่ส่ง code รายการ feature หรือบทสนทนานี้

ถ้าสร้าง agent แยกไม่ได้ ให้ session หลักทดสอบเองก่อนเปิดอ่าน code ใด ๆ และระบุข้อจำกัดนี้ในรายงาน

### กฎความไม่ perfect

ส่งกฎชุดนี้ให้ผู้ทดสอบตามตัวอักษร

- ตัดสินใจจากภาพหน้าจอเท่านั้น ใช้เครื่องมืออ่านโครงสร้างหน้าได้เฉพาะเพื่อกดสิ่งที่ตัดสินใจไว้แล้ว ไม่ใช้เพื่อหาคำตอบ
- อ่านเฉพาะหัวข้อ ข้อความบนปุ่ม และตัวอักษรขนาดใหญ่ ข้อความที่ยาวเกินสองบรรทัดถือว่าไม่ได้อ่าน
- คลิกสิ่งแรกที่ดูใช่ ไม่ไล่ดูทุกตัวเลือกก่อน
- ไม่ scroll เว้นแต่หน้าจอมีสัญญาณชัดว่ายังมีเนื้อหาต่อ
- ไม่พิมพ์ URL เอง ไม่เดาจากที่อยู่หน้าเว็บ ไม่ใช้คีย์ลัด
- ในฟอร์มแรกที่เจอ ให้กรอกผิดหนึ่งช่องแบบที่คนทำบ่อย เช่น วันที่ผิดรูปแบบ หรือเว้นช่องบังคับ เพื่อดูว่าแอปบอกทางแก้อย่างไร
- พลาด 3 ครั้งในงานเดียว ให้เลิกงานนั้นและบันทึกว่าเลิกตรงไหน
- ก่อนคลิกทุกครั้ง เขียนหนึ่งบรรทัดว่าเห็นอะไรและคาดว่าจะเกิดอะไร หลังคลิก เขียนว่าเกิดอะไรจริง
- อย่าแสดงความงงที่ไม่ได้เกิดจากกฎ ทำตามกฎแล้วบันทึกสิ่งที่เกิดขึ้นจริง

### สองรอบต่อบทบาท

**รอบไม่รู้อะไรเลย** ไม่บอกงาน ให้ดูหน้าแรกแล้วเขียนทันทีว่า แอปนี้มีไว้ทำอะไร ฉันทำอะไรได้ที่นี่ และจะกดอะไรก่อน จากนั้นให้ลองเริ่มทำสิ่งที่คิดว่ามีประโยชน์ไม่เกิน 5 การกระทำ

**รอบรู้งาน** ทำงานหลักทีละงาน รวมงานส่งไม้ต่อ บันทึกต่องานว่า สำเร็จหรือไปไม่ถึง จำนวนคลิก จำนวนคลิกผิด จำนวนครั้งที่ย้อนกลับ จุดที่ติด และ screenshot ทุกจุดที่ติด

**คำถามปิดท้าย** ถามผู้ทดสอบว่า "แอปนี้ทำอะไรได้บ้าง" ให้ตอบจากที่เห็นมาเท่านั้น คำตอบนี้ใช้เทียบกับรายการ feature เพื่อหาสิ่งที่ไม่มีใครเจอ

### มาตรวัดความยาก

จำนวนคลิกของผู้ทดสอบจำลองแกว่งได้ จึงให้รันรอบรู้งานอย่างน้อย 2 ครั้งต่อบทบาทด้วยผู้ทดสอบตัวใหม่ แล้วแสดงเป็นช่วง เช่น "8-11 คลิก" งานที่ไปไม่ถึงให้รายงานว่า "ไปไม่ถึง" ซึ่งถือว่ายากกว่าตัวเลขใด ๆ มาตรวัดนี้ใช้ดูว่างานไหนหนัก ไม่ใช้เป็นเกณฑ์ผ่านหรือตก เพราะการไล่ลดคลิกอย่างเดียวพาไปสู่แอปที่จืด

## ขั้นที่ 3 — ตรวจ class

ผู้ตรวจเป็นอีกเลนส์หนึ่ง ไม่ใช่คนงง ดู screenshot ที่เก็บมาเทียบกับลายเซ็นของแอป แล้วเขียนต่อหน้าจอว่า คงลายเซ็น จืดเหมือน template หรือผิดลายเซ็น พร้อมเหตุผลหนึ่งบรรทัด คำถามที่ใช้คือ "ปิดโลโก้แล้วยังรู้ไหมว่าเป็นงานของเรา"

ผู้ตรวจ class ติงได้ แต่ยับยั้งการทำให้ง่ายไม่ได้

## ขั้นที่ 4 — รายงาน

ใช้ชื่อเรียกธรรมดาสำหรับทุกปัญหา เช่น "หาปุ่มเริ่มรายงานไม่เจอ" ไม่ใช้รหัสอ้างอิง ใช้เลขลำดับ 1, 2, 3 ได้เมื่อผู้ใช้ต้องเลือก

โครงรายงาน:

1. **สรุปหนึ่งย่อหน้า** สามเรื่องที่สำคัญที่สุด
2. **ความเข้าใจใน 10 วินาทีแรก** ต่อบทบาท เทียบสิ่งที่ผู้ทดสอบเข้าใจกับสิ่งที่แอปตั้งใจ
3. **มาตรวัดความยากต่องาน** ตาราง: บทบาท งาน ผล ช่วงจำนวนคลิก คลิกผิด ย้อนกลับ
4. **กอง "พังจริง"** แต่ละข้อมีชื่อ บทบาท ตำแหน่ง screenshot ขั้นตอนทำซ้ำ และความหนัก (กั้นไม่ให้ไปถึงเป้าหมาย ทำให้ช้า หรือน่ารำคาญ)
5. **กอง "ต้องถามคนจริง"** แต่ละข้อเขียนเป็นสมมติฐาน พร้อมหลักฐานว่าผู้ทดสอบติดตรงไหน
6. **รอยต่อระหว่างบทบาท** งานที่ส่งแล้วไปถึงไหม อีกฝั่งหาเจอไหม งานตีกลับย้อนมาถึงไหม
7. **Feature ที่ไม่มีใครหาเจอ** ติดธงทุกตัว บอกว่าอยู่ตรงไหนในแอป และให้ผู้ใช้เลือกทางออกเป็นรายตัว คือทำให้หาเจอง่ายขึ้น หรือตัดทิ้ง
8. **ข้อติงเรื่อง class**
9. **บททดสอบ 15 นาทีกับคนจริง** เลือกสมมติฐานที่สำคัญที่สุด 3 ข้อ แต่ละข้อบอกว่าให้คนทำอะไร ให้สังเกตอะไร และเกณฑ์ตัดสินว่าสมมติฐานยืนหรือตก
10. **ข้อจำกัดของรอบนี้** อะไรไม่ได้ทดสอบ และผู้ทดสอบเป็น agent แยกหรือไม่

### วิธีแบ่งกอง

ข้อใดจะอยู่กอง "พังจริง" ได้ ต้องเป็นสิ่งที่ใครดูหลักฐานแล้วตัดสินตรงกันโดยไม่ต้องรู้ว่าผู้ใช้รู้สึกอย่างไร เช่น ปุ่มไม่ทำงาน ทางตัน ป้ายไม่ตรงกัน ข้อมูลหาย หรือบทบาทเห็นสิ่งที่ไม่ควรเห็น

ทุกอย่างที่เกี่ยวกับความเข้าใจของคนอยู่กอง "ต้องถามคนจริง" รวมถึง feature ที่ไม่มีใครหาเจอ และข้อติงเรื่อง class ถ้าลังเลว่าอยู่กองไหน ให้ใส่กองสอง

ส่งรายงานเป็นเอกสารที่เปิดอ่านและส่งต่อได้ ถ้าเข้าถึง code ให้บันทึกไว้ในโปรเจกต์ด้วย Mode feedback จบที่ขั้นนี้

## ขั้นที่ 5 — ผู้ใช้เลือกว่าจะแก้อะไร

เสนอรายการให้ผู้ใช้เลือก ผู้ใช้เลือกจากกอง "พังจริง" ได้ทันที ส่วนข้อในกอง "ต้องถามคนจริง" จะแก้ได้เมื่อผู้ใช้ยืนยันเอง หรือหลังทดสอบกับคนจริงแล้ว สำหรับ feature ที่ไม่มีใครหาเจอ ให้ผู้ใช้เลือกทางออกเป็นรายตัว

ยังไม่แตะ code จนกว่าผู้ใช้จะเลือก

## ขั้นที่ 6 — แก้แอป

- แก้เฉพาะข้อที่ผู้ใช้เลือก ไม่ปรับปรุงส่วนอื่นไปด้วย
- ลำดับทางแก้ที่ควรลองก่อน: ตัด แล้วรวม แล้วเปลี่ยนชื่อหรือย้ายตำแหน่ง แล้วเพิ่มคำอธิบายสั้น ๆ การเพิ่ม feature เป็นทางสุดท้ายและต้องให้ผู้ใช้เห็นชอบก่อน
- การตัด feature ต้องได้รับการยืนยันจากผู้ใช้เป็นรายตัวเสมอ
- เมื่อความง่ายกับ style ชนกัน ความง่ายชนะ จากนั้นแต่งสิ่งที่ง่ายแล้วให้ตรงลายเซ็นของแอป
- แก้ทีละข้อเป็นการเปลี่ยนแปลงแยกกัน เพื่อให้ย้อนกลับได้ทีละข้อ และรัน test ที่มีอยู่ของโปรเจกต์

## ขั้นที่ 7 — คนงงคนใหม่มาลองซ้ำ

สร้างผู้ทดสอบตัวใหม่ที่ไม่รู้ว่าแก้อะไรไป ให้ทำงานชุดเดิมด้วยกฎเดิม ผู้แก้ต้องไม่บอกใบ้อะไรกับผู้ทดสอบ เพราะคนแก้ที่ตรวจงานตัวเองมักเห็นว่าผ่าน

รายงานต่อข้อที่แก้ว่า หาย ยังอยู่ หรือเกิดปัญหาใหม่ แสดงมาตรวัดความยากก่อนกับหลังเป็นช่วง และตรวจ class เฉพาะหน้าจอที่เปลี่ยน ถ้ามีอะไรแย่ลง ให้บอกตรง ๆ และเสนอย้อนกลับ

ทำหนึ่งรอบเป็นค่าเริ่มต้น ถามผู้ใช้ก่อนทำรอบถัดไป

## สิ่งที่ควรเลี่ยง

- ให้ผู้ทดสอบเห็น code รายการ feature หรือรู้ว่าเพิ่งแก้อะไร
- รายงานสิ่งที่เดาเหมือนเป็นข้อเท็จจริง
- แก้ข้อในกอง "ต้องถามคนจริง" โดยไม่มีใครยืนยัน
- แสดงจำนวนคลิกเป็นเลขเดียว หรือใช้เป็นเกณฑ์ผ่าน
- แก้ความงงด้วยการเพิ่ม feature หรือเพิ่มคำอธิบายยาว ๆ
- ทดแทนการใช้แอปจริงด้วยการอ่าน code
